# Профилирование рендерера и слоя вида на движке (`src/engine/`, `src/view/engine/`)

GPU и браузера в этом окружении нет, поэтому отчёт состоит из двух частей:

1. **Статический разбор покадрового бюджета** — что и сколько раз вызывается за кадр, какие буферы/текстуры
   аплоадятся, сколько draw call, где readback. Всё с `file:line`.
2. **Микробенчмарки CPU-части**, которая реально считается на JS (`perf/bench/gfx/`), медиана из ≥5 прогонов после
   прогрева. Другие агенты работают в этом же чекауте, поэтому абсолютные числа завышены конкуренцией за CPU:
   сравнивать надо кейсы внутри одной таблицы и масштабировать по числу вызовов за кадр.

Бюджет: 60 fps → **16.6 мс** на кадр, из них CPU-часть движка (всё, что ниже) — это то, что мы измеряем; GPU-часть
оценивается по числам из кода (треугольники, инстансы, проходы, размеры буферов).

### 1.1. Что делается каждый кадр, хотя меняется редко

| Работа | Цена | Почему это «зря» |
|---|---|---|
| `noteCasters()` — хеш **всей** таблицы заданий леса (36 слов × jobCount) с `Math.imul` | 0.0128 мс при 400 заданиях, 0.0314 мс при 1000 (`forest.ts:269-275`, вызов `forest.ts:264`) | Таблица меняется только при движении камеры на шаг тайла/зума; хеш же считается 60 раз в секунду. |
| `forest.prepare` — обход ~1600-6900 тайлов, `thinReach` (30 бисекций по 1600 тайлам), `blockShares` на тайл, сортировка `[...trees, ...details]` | 0.059 (обход) + 0.094 (`thinReach`) + ~0.1 (оценка на `blockShares`/стол) = **~0.25-0.3 мс** | При стоящей камере результат идентичен предыдущему кадру. |
| `buildView` + `cameraAxes` + `ecefToGeodetic` | 0.0019 + 0.0003 + 0.0004 | Матрицы меняются только при движении камеры; можно кэшировать по `(lat,lng,h,distance,heading,pitch,size)`. |
| `frustumPlanes` + 6 плоскостей | 0.0003 | Считается заново каждый кадр в `forest.ts:291`. |
| `overlay.update`: `levels.map` + 3 `levelSquare` + `shown.map` | ~0.01 | Тривиально, но аллоцирует 2 массива на 45 элементов каждый кадр (`overlayRaster.ts:149`). |
| `overlay` перерастеризация 3 уровней 2048² при изменении данных игры | 3 полных прохода + ≤135 draw на уровень | Любое завершение стройки/дороги/процента расчистки → `setData` → `dirty` (`overlayRaster.ts:127-139`). |
| `life` — позиции жителей и **перезапись всех фигур** | 0.135 (600 жителей, `placeAt`/`standAt`) + 0.0094×N фигур (поза+запись) | До 108 фигур (бюджет `FIGURE_VERTICES = 120 000`, `life.ts:33`) → **~1.0 мс + 4.2 МБ загрузки** каждый кадр вблизи. |
| `placeLabels`/`gameLabels` — проекция всех имён, `pickLabels`, лучи видимости, запись `style.transform` | 0.03-0.9 (`pickLabels` на 1000 боксов = 0.85) + 0.6 (48 лучей) | Имена меняются при смене тайлов/зума; луч видимости отдаётся раз в 200 мс на метку (`labelSight.ts:19`), но бюджет 48 лучей **на слой** — до 3×48 = 144 луча/кадр. |
| `rowBounds.set([...node.center, node.radius], …)` | 261 аллокация массива на кадр | `terrain.ts:373` — spread создаёт массив на каждый узел каждый кадр. |
| Статистика (`statsHud`) | 4 раза в секунду | ок. |

## 4. Топ-хотспоты с `file:line`

1. **Фигуры жителей переписываются и загружаются каждый кадр.** `life.ts:169-203` (цикл), `life.ts:182`
   (`writeVillager`), `townMesh.ts:210-219` (`fill` → `writeBuffer`), бюджет `life.ts:33`
   (`FIGURE_VERTICES = 120 000`). Измерено: 0.0094 мс на фигуру → **до 1.0 мс и 4.2 МБ загрузки на кадр**
   (120 000 × 9 float × 4 Б). Для сравнения — весь бюджет вершинных сборок ландшафта 2.1 МБ/кадр (`terrain.ts:42`).
2. **`pickLabels` + проекция меток каждый кадр.** `labelLayout.ts:31-46` (O(n²) по показанным),
   `placeLabels.ts:128-165`, `gameLabels.ts:128-180`. Измерено: 0.85 мс на 1000 кандидатов + 0.62 мс на проекцию
   6000 имён; при сотнях имён — 0.1-0.3 мс, но при зуме «из космоса в город» — до 1.5 мс в одном кадре.
3. **Лучи видимости меток/маркеров.** `engine.ts:175` (`behindTerrain`) → `pick.ts:13-53`
   (`MAX_STEPS = 4000`), бюджет `labelSight.ts:11` (48 лучей на слой). Измерено: 0.0115 мс на луч →
   **0.61 мс на 48 лучей**, до 1.8 мс при трёх слоях в одном кадре.
4. **`forest.prepare` каждый кадр.** `forest.ts:279-408`, `thinReach` (`forestTiles.ts:25-36`),
   `noteCasters` (`forest.ts:269-275`, хеш 36 слов × число заданий). Измерено: 0.059 + 0.094 + 0.013 = **0.17 мс**
   (плюс оценка на `blockShares`/стол ~0.1 мс) — при стоящей камере результат не меняется.
5. **Слияние и перезаливка городского меша на каждое изменение.** `models.ts:131-147` (`merge` + `setRoads`/
   `setBuildings`), `townMesh.ts:275-284` (новые `GPUBuffer` + `writeBuffer`). Измерено: слияние 800 домов —
   **6.3 мс и 37-40 МБ** загрузки, плюс уничтожение/создание буферов.
6. **Геометрия оверлея из earcut на каждое изменение данных.** `geometry.ts:93`, `overlayRaster.ts:127-139`.
   Измерено: один rebuild всех типовых фигур — **14.5 мс**, из них 5.6 мс — 120 полей по 128 вершин.
7. **`terrain.update`: аллокации в цикле по узлам.** `terrain.ts:373` (`rowBounds.set([...node.center, …])`),
   `terrain.ts:415-437` (`grantDrape` — `order.sort` с компаратором по 100-260 узлам каждый кадр),
   `terrain.ts:509-517` (`evict`: массив на 1024 слота + сортировка).
8. **`buildNodeVertices` при появлении узлов.** `terrain.ts:278, 496-501`, `nodeMesh.ts:48-79`. 0.0082 мс и 34 КБ
   на узел, до 64 за кадр = **0.52 мс + 2.1 МБ**.

## 5. Риски производительности GPU (числа из кода)

### 5.1. Постоянная память GPU ≈ 294 МБ

| Что | Размер | `file:line` |
|---|---|---|
| height pages `r32float`, 258×258 × **512** слоёв (`maxTextureArrayLayers`, запрошено 512) | 0.27 МБ × 512 = **130 МБ** (при лимите 256 — 65 МБ) | `heightPages.ts:51-58`, `device.ts:20-33` |
| drape pages `rgba8unorm-srgb` 256×256 × 256 | **64 МБ** | `drapePages.ts:49-53`, `terrain.ts:45` |
| cover pages `r8uint` 256×256 × 256 | **16 МБ** | `drapePages.ts:54-59` |
| overlay 2048×2048 × 3 `rgba8unorm-srgb` | **48 МБ** | `overlayRaster.ts:59-66` |
| shadow maps `depth32float` 2048² × 4 (high) | **64 МБ** | `shadowMap.ts:13-16, 161-166` |
| forest instances (565 248 × 32 Б, см. §5.2) | **17.3 МБ** | `forest.ts:166-167, 619-628` |
| terrain vertex slots (1024 × 34 848 Б) | **34 МБ** | `terrain.ts:130` |
| weather cube 192²×6×2 + 3D-шум | ~2 МБ | `weather.ts:99-108` |
| cloud target `rgba16float` 0.75×canvas (1600×900 CSS) | 6.2 МБ | `clouds.ts:123-140` |
| MSAA color+depth 4× при 3200×1800 (dpr 2) | **176 МБ** | `device.ts:13`, `engine.ts:211-218` |

Итого «каркас» ≈ **294 МиБ** при лимите 256 слоёв страниц (≈**359 МиБ** при 512 слоях, которые просит `device.ts:20-33`)
плюс MSAA-таргеты (176 МиБ при dpr 2) — на слабых iGPU это первое, что упрётся.

### 5.2. Число draw call

| Проход | Draw call | `file:line` |
|---|---|---|
| occluders (ландшафт + город) | 1 + до 6 | `engine.ts:258-266`, `terrain.ts:439-443`, `townMesh.ts:46, 234-251` |
| main, непрозрачные: поля 1, лес **12** (6 моделей + 6 импостеров), точки ≤3 | 16 | `forest.ts:466-484`, `dots.ts:132-140` |
| main, небо | 1 | `sky.ts:25-28` |
| main, прозрачные: дым 1, облака 1, осадки 1 | 3 | `smoke.ts:31`, `clouds.ts:42, 166-172`, `precip.ts:25` |
| shadow: на каждый каскад ландшафт (по прогонам) + город 2 + лес ≤15 | **до ~20 × 4 = 80** | `forest.ts:486-510`, `shadowMap.ts:150-158` |
| overlay при rebuild: 45 слоёв × ≤3 draw × ≤3 уровня + 3 прохода 2048² | **до 405** | `overlayRaster.ts:181-218` |

Итого в норме **27 draw call** на кадр (7 occluders + 20 main), но при `shadowVersion`-флапе (движение камеры/
стриминг страниц) — до 107, а при изменении игровых данных — ещё до 405 в overlay-проходе.

### 5.3. Лес: 3 млн кандидатов и 565 248 инстансов

* `MAX_CANDIDATES = 3 000 000` (`forest.ts:34`), `@workgroup_size(64)` → **46 875 групп** на кадр
  (`forestScatter.wgsl:155`), каждая нить — frustum-тест, выбор по дистанции, поиск в Hi-Z, шум/порода.
* Таблица слотов (`slotCaps`, `forest.ts:619-628`): 3 вида деревьев × (24 576 + far) + 3 детали × (12 288 + 69 632),
  где `far(share·120 000)` округляется вверх до 4096. Максимумы долей: хвойные 0.85 → 114 688, широколиственные
  0.9 → 122 880, берёза 0.045 → 8192. **Сумма 565 248 инстансов × 32 Б = 17.3 МБ** (`forest.ts:166-167`).
* Ожидаемое число деревьев: `MAX_TREES = 120 000`, `MAX_DETAILS = 60 000` (`forest.ts:31-32`) — бюджет
  подгоняется `thinReach` (`forestTiles.ts:25-36`), т.е. на GPU реально рисуется ≤ ~180k инстансов.
* Загрузка на кадр: таблица заданий `jobCount × 144 Б` (~58 КБ при 400 заданиях, `forest.ts:379`), юниформы ~1 КБ.

### 5.4. Readback'и и синхронизация

| Что | Частота | Влияние |
|---|---|---|
| `GpuTimer.afterSubmit` → `mapAsync` 16 Б, кольцо из 8 буферов (`timer.ts:20-56`) | **каждый кадр** | скрыто кольцом, но это точка синхронизации очереди каждый кадр; при 8 занятых слотах кадр просто не мерится |
| Статистика scatter'а: `copyBufferToBuffer` + `mapAsync` 64 Б + `.slice()` (`forest.ts:443-462`) | раз в 250 мс (`STATS_MS`) | ок, но `slots = [...c.subarray(...)]` + `reduce` аллоцируют |
| `Forest.setMask` → уничтожение/создание текстуры маски (`forest.ts:254-260, 569-576`) | на каждое изменение застройки/дорог/зон/расчистки (с дебаунсом через `effect`, `view/engine/forest.ts:75-84`) | создание текстуры до 2048² (16 МБ) — заметный хитч |

### 5.5. Пересоздание пайплайнов

Все пайплайны создаются в конструкторах: terrain 2 (`terrain.ts:159-180`), forest 6
(`forest.ts:184-247`), sky 1 (`sky.ts:14-22`), clouds 2 (`clouds.ts:98-119`), overlay 3
(`overlayRaster.ts:68-106`), townMesh ≈6, dots/precip/smoke/fields по 1. **Пайплайны за кадр не пересоздаются** —
это хорошо. Пересоздаются при смене качества: `ShadowMap.resize` (64 МБ, `shadowMap.ts:161-166`),
`WeatherGpu.resizeCubes` (`weather.ts:126-134`), и при ресайзе окна — MSAA-таргеты + `Clouds.target`.

### 5.6. Ресайз окна: пересоздание 176 МБ на каждый кадр драга

`engine.ts:127-137`: `ResizeObserver` при **каждом** изменении размера вызывает `this.frame()`, а `fitCanvas`
(`engine.ts:211-218`) уничтожает и создаёт `msaa color` и `depth` (при 3200×1800×4×4 Б = по 88 МБ). При
перетаскивании края окна это 2 аллокации по 88 МБ **на кадр**. То же в `clouds.ts:126-140`.

### 5.7. Облака и дым

* Raymarch облаков: `PRESETS.high` = 0.75× разрешения, **80 шагов** + 6 шагов к солнцу (`cloudQuality.ts:18-21`),
  пересчёт при сдвиге игровых часов на 5 минут, смене вида/размера/качества или вспышке молнии
  (`needsMarch`, `cloudQuality.ts:63-72`; `weather.ts:271`). На глобусе при движении камеры — **каждый кадр
  полный экран × 80 шагов**.
* Дым: `PUFFS = 12` квадов на трубу, `MAX_CHIMNEYS = 400`, `REACH = 950` м (`smoke.ts:13-17`); при смене вида
  сортировка всех труб (`smoke.ts:116-136`) — 0.0005-0.002 мс, не критично.
* Инстансы леса в тени: в грубых каскадах модели заменяются квадами (`forest.ts:486-510`), но всё равно
  ≤15 draw call на каскад.

## 7. Предлагаемые правки

| # | Правка | Где | Ожидаемый выигрыш | Риск |
|---|---|---|---|---|
| 1 | **Не переписывать всех фигур каждый кадр**: обновлять позу только при смене действия/направления и не чаще 20-30 Гц, а в остальные кадры поднимать уже загруженные вершины через uniform времени (шейдерная анимация шага) либо интерполировать матрицы частей в юниформе | `life.ts:169-203`, `townMesh.ts:210-219` | −0.7…1.0 мс CPU и −3…4 МБ/кадр загрузки (≈−180 МБ/с шины) | средний: нужен шейдерный путь для шага; визуально ноги станут «гладкими» |
| 2 | **Кэш кадра для меток**: `pickLabels` и проекция только при изменении вида (матрица/размер/данные), а не 60 раз/с; строку `transform` строить один раз и обновлять при сдвиге > 0.5 px | `placeLabels.ts:128-165`, `gameLabels.ts:128-180` | −0.1…0.3 мс в норме, −1.2 мс в пике (зум/панорама), плюс меньше работы стилю | низкий: нужен ключ «вид не менялся» |
| 3 | **Сетка для `pickLabels`** (разбиение экрана на клетки 64×64) вместо O(n²) | `labelLayout.ts:31-46` | 1000 боксов: 0.85 → ~0.05 мс (оценка) | низкий: эквивалентность выбора надо покрыть тестом |
| 4 | **`forest.prepare` только при сдвиге камеры на порог** (матрица вида + reach): кэшировать job-таблицу и юниформы, `noteCasters` — по версии таблицы, а не хешем 36×N слов каждый кадр | `forest.ts:279-408`, `forest.ts:269-275` | −0.25…0.3 мс/кадр, −0.013 мс хеша | низкий-средний: нужно точно инвалидировать при стриминге страниц покрытия |
| 5 | **Инкрементальная заливка города**: держать меши по предметам и обновлять только изменившийся сегмент (`writeBuffer` по смещению) вместо `merge` всего города | `models.ts:131-147`, `townMesh.ts:275-284` | слияние 800 домов 6.3 мс → ~0.1 мс; загрузка 40 МБ → ~50 КБ на изменение | средний: нужен аллокатор сегментов в буфере, зато исчезают хитчи на каждой стройке |
| 6 | **Оверлей: пересобирать только изменившийся слой и не все 3 уровня** (уровень 24×distance меняется редко) + `earcut` кэшировать по геометрии фичи | `overlayRaster.ts:143-215`, `geometry.ts:88-100` | rebuild 14.5 мс → 2-4 мс; 405 draw → ≤135 | низкий |
| 7 | **Ресайз: не пересоздавать MSAA-таргеты на каждый пиксель драга** — менять размер canvas сразу, а текстуры пересоздавать по таймауту 100-150 мс после последнего события | `engine.ts:127-137, 211-218` | убирает 2×88 МБ аллокаций за кадр драга | низкий |
| 8 | **`RIGS_KEPT`: LRU вместо `clear()`** и пред-прогрев ригов ближайших жителей | `life.ts:68-76` | убирает 15 мс пик после каждого `clear()` | низкий |
| 9 | **Лучи видимости: считать один луч на несколько меток** (общий сектор) или снизить `RAYS_PER_FRAME` при >60 fps | `labelSight.ts:11`, `pick.ts:28-52` | до −1.2 мс в пиковом кадре | низкий: возможны мигания «спрятанных» меток |
| 10 | **Аллокации в цикле узлов**: писать `rowBounds` по индексам, а не `set([...])`; `grantDrape` — переиспользуемый буфер + сортировка индексов | `terrain.ts:373, 415-437` | −0.02…0.05 мс/кадр и меньше GC-пауз | низкий |

Суммарно правки 1-4 и 9 снимают ≈1.5-2.5 мс с CPU-бюджета вблизи и убирают многомегабайтные загрузки за кадр;
5-7 убирают хитчи на игровых событиях и ресайзе; 8, 10 — гигиена.
