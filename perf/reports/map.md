# Производительность интерактивных инструментов и клиентской геометрии (`src/map/`)

Замеры: `perf/bench/map/` (vitest, Node 22, медиана из 5–11 прогонов после прогрева). Абсолютные числа завышены
конкуренцией за CPU (в чекауте работают другие агенты), поэтому выводы строятся на сравнении размеров и на бюджете
4–6 мс на событие. Всё, что не измерено харнессом, помечено как **оценка** или **по коду**.

Команда:

```
npx vitest run --config vitest.perf.config.ts perf/bench/map/roads.test.ts   --reporter=verbose
npx vitest run --config vitest.perf.config.ts perf/bench/map/pointer.test.ts --reporter=verbose
```

## 1. Что реально выполняется на каждое событие

### 1.1 Частота и троттлинг

| Инструмент | Обработчик | Троттлинг | Что происходит на каждое событие |
|---|---|---|---|
| `roadTool` | `view.on("pointermove", onMove)` — `src/map/roadTool.ts:1012`, тело `:687-775` | **нет** (только сэмплирование рельефа, `PREVIEW_MS = 120` — `roadTool.ts:24`, `:263-291`) | `snapPoint` + 1–2 `overlay.setData` + `addRoad` (валидация) + при отсутствии начала — `nearestEdge` по всем рёбрам |
| `strokeTool` | `src/map/strokeTool.ts:484`, тело `:353-372` | **есть**: `requestAnimationFrame` — `strokeTool.ts:213-215` | `spansAlong` + `planStroke` (планировщик сима на главном потоке) + `setData` плана |
| `placeTool` | `src/map/placeTool.ts:386`, тело `:276-284` | **нет** (только `siteAt` рельефа, `SAMPLE_DELAY_MS = 150` — `placeTool.ts:41`, `:196-202`) | `nearestStart` (бакеты) + `makeBuilding` + `canPlace` + `previewServiceCoverage` + 2 `setData` |
| `landTool` | `src/map/landTool.ts:331`, тело `:250-268` → `showDraft` `:112-162` | **нет** (только `analyzeField`, `ANALYZE_MS = 200` — `landTool.ts:18`, `:145-160`) | `validateField`/`validateClearing` + копия footprint'ов всех зданий + `setData` черновика |
| `revealTool` | `src/map/revealTool.ts:28-33` | нет | 64-шаговое кольцо + `setData` (только DEV, `src/main.ts:106`) |
| слой зданий | `src/view/layers/buildings.ts:174-179` | нет (ранний выход, пока активен инструмент) | `buildingAt` → запрос индекса |

Каждый `view.on(...)` — отдельная подписка, и в каждой `dispatch` сначала делается **луч в рельеф**
`engine.pick(point[0], point[1])` — `src/view/engine/view.ts:97-101`. При активных инструментах подписок на
`pointermove` пять (`roadTool`, `strokeTool`, `placeTool`, `landTool`, `revealTool`), т.е. **5 лучей на одно движение**
(стоимость лучей не измерена — движок требует WebGPU; **оценка**).

### 1.2 Цепочка `roadTool.onMove` (рисование, есть начало цепочки)

`roadTool.ts:1012 onMove` → `context()` `:306-316` (`frame.toLocal`) → `aim()` `:317-324` → `resolve()` `:234-242` →
`snapPoint` (`src/sim/roads.ts:87`, полный проход по узлам, затем по рёбрам) → `setSnap()` `:243-250` (`setData("road-snap")`)
→ `showPath()` `:325-362` → `drawPreview()` `:215-231` (`setData("road-preview")`) → `addRoad(g, pts, t, 1, …)`
(`src/sim/roads.ts:208`) — **полная валидация на копии графа** → `requestCost()` `:263-291` (единственное, что
троттлится: `setTimeout(…, 120)` + `samplePathProfile`).

Без начала цепочки (`start === null`) добавляется `upgradeRunAt()` `:437-458` → `nearestEdge()` `:291-305` (перебор всех
рёбер) → `runAt()` `:115-134` (при смене идентичности графа — полный `roadChains`).

### 1.3 Что делает `addRoad` на каждое движение (и это главное)

`src/sim/roads.ts:208-311`: `cloneGraph` `:118` (раскладка всех узлов и рёбер), затем **на каждый сегмент линии**:

- `for (const e of Object.values(g.edges)) … overlapLength` — `:238-242`;
- `for (const id of Object.keys(g.edges).map(Number))` — `:268` (две аллокации массива на сегмент) и проверки пересечений;
- `for (const e of Object.values(g.edges)) …` — `:305-309` (ещё один проход на каждое звено цепочки после разбиений).

Итого `O(точек × рёбер)` с аллокациями. Никакого пространственного индекса рёбер нет.

### 1.4 Сброс кэшей: на движение или на снапшот?

- `memo.ts:6-13` (`makeIdentityCache`) и `roadNetCache.ts:9` — ключ по идентичности объекта. Клиентский `state`
  пересобирается на каждом снапшоте (`src/simClient.ts:158`), значит `roads` — новый объект: `roadNet`, `chains`
  (`view/layers/roads.ts:31`), `edgeState` пересчитываются **раз за снапшот** (2.5 с на 1×), не за движение.
- Превью-валидация `addRoad` работает на полученной копии и **не пишет** в сигнал `roads` (`roadTool.ts:347`, `:378`;
  `commitPath` `:389` — отдельный путь), поэтому кэши движением **не сбрасываются**.
- `runAt` (`roadTool.ts:115-134`) кэширует по идентичности графа — сброс только на снапшот.
- `hitIndexOf` (`view/layers/buildings.ts:24-30`) кэширует по строке `buildingSet` — перестройка только при
  появлении/исчезновении зданий.

Вывод: кэши не «сбрасываются на каждое движение»; проблема не в них, а в том, что часть работы на движение не кэшируется
вовсе (валидация `addRoad`, `planStroke`, `validateField`).

### 1.5 Оверлеи: `setData` → пересборка буферов + перерисовка всех трёх уровней

`src/engine/overlay/overlayRaster.ts:127-139` — каждый `setData` освобождает GPU-буферы всех слоёв этого источника
(`free(b)`, `b.destroy()`) и ставит `dirty = true`; в `update()` условие `if (!this.dirty && …) continue` (`:162`)
означает, что при `dirty` перерисовываются **все три уровня** 2048² (`:155-172`). За одно движение `roadTool` пишет
2–3 источника (`road-snap`, `road-preview`, иногда `road-hover`) — то есть максимум один кадр перерисовки (события
схлопываются в кадр), но с полной пересборкой геометрии каждого источника: `buildLayer` (`engine/overlay/geometry.ts:71`).

## 4. Топ-хотспоты

1. **`addRoad` как валидация превью — `O(точек × рёбер)` с аллокациями.**
   `roadTool.ts:347` → `sim/roads.ts:208`; три прохода по всем рёбрам на каждый сегмент: `:238`, `:268`
   (`Object.keys(g.edges).map(Number)` — две аллокации), `:305`; плюс `cloneGraph` `:118`.
   5.4–10.5 мс на изогнутое превью — это уже весь бюджет одной операцией.
2. **`canPlace` внутри `planStroke`.** `sim/stroke.ts:182` → `sim/growth.ts:163-193`: `Map` по всем ячейкам
   (`:178-179`) и хеш занятости по всем зданиям (`:96-101`, зовётся в `:180`) — **на каждого кандидата**.
   Даёт 4.0 мс из 4.3 мс кадра при 300 зданиях и 8.0 из 7.6 при 600.
3. **Слой дорог на каждом снапшоте.** `view/layers/roads.ts:31-85` (chains + junctions + `itemSig` по всем цепочкам)
   и `view/engine/models.ts:103-160` (меш на каждый item): 3.2 / 10.4 / **23.5 мс** при 50/200/500 рёбрах.
   Драйвер — аппероны узлов: 20.4 мс из 23.5 при 499 узлах (`roadJunctions.ts:165`).
4. **`overlay.setData` на каждое движение.** `overlayRaster.ts:127-140`: освобождение GPU-буферов + `dirty`, затем
   перерисовка **всех трёх уровней** 2048² (`:155-172`). 2–3 источника за движение `roadTool.ts:249`, `:221`, `:461`.
   CPU-часть (геометрия) 0.03–0.37 мс на источник; GPU-часть в Node не измерена — **по коду** это три прохода
   2048×2048 + загрузка текстур на любой `dirty` кадр.
5. **Нет троттлинга у `roadTool`/`landTool`/`placeTool`** (в отличие от `strokeTool.ts:213-215`): при мыши 125 Гц
   вся работа выполняется 2–8 раз за кадр. `roadTool` при этом ещё и делает `addRoad` на каждое событие.

## 5. Предлагаемые правки

### Правка 1. Убрать `canPlace` из внутреннего цикла `planStroke` (главный выигрыш)

Один раз на план построить то, что `canPlace` пересобирает каждый раз: карту ячеек по `edge:side` и хеш занятости
(вынести `growth.ts:178-181` и `:96-101` в помощник, кэшируемый по идентичности `zones`/`buildings` через
`makeIdentityCache`, `sim/memo.ts:6`), и проверять кандидата по ним.

- **Ожидаемый выигрыш:** 4.0 → 0.4–0.8 мс (≈6–10×) на кадр при 300 зданиях; 8.0 → ~0.8 мс при 600 — бюджет
  восстанавливается с запасом на 900-м перетаскивании.
- **Риск:** средний. Правила обязаны остаться идентичными (те же причины отказа), а `canPlace` используется и
  воркером — менять только внутреннюю реализацию, не контракт; нужны существующие тесты `sim/stroke.test.ts`,
  `sim/growth.test.ts` плюс сверка `applyStroke` (воркер планирует заново).

### Правка 2. Троттлить `roadTool.onMove` и не звать `addRoad` без изменения пути

Коалесцировать события в rAF (как `strokeTool.ts:213-215`) и пропускать пересчёт, если сдвиг < 1 м; `addRoad`
(локальный вердикт, `roadTool.ts:347`) — только на «устоявшемся» пути, а цвет превью брать из предыдущего вердикта.

- **Ожидаемый выигрыш:** изогнутое превью 5.4–10.5 мс за событие → ≤0.5–1 мс в среднем за кадр (в 5–10 раз меньше
  нагруженных событий); прямая линия и так 0.035 мс. Бюджет соблюдается даже на 1000 рёбер.
- **Риск:** низкий. Максимальная задержка метки/цвета 16 мс — незаметно; `commitPath` на клик не тормозится.

### Правка 3. Перестать пересканировать все рёбра внутри `addRoad`

Дешёвый вариант (низкий риск): вынести `Object.values(g.edges)` и список id из циклов сегмента
(`sim/roads.ts:238`, `:268`, `:305`) в переменные на вызов и заменить `Object.keys(g.edges).map(Number)` на уже
собранный массив id; `cloneGraph` (`:118`) заменить на копию только при первом изменении (copy-on-write по факту
`splitEdge`/добавления).
Дорогой вариант (средний/высокий риск): сетка рёбер (как `buildingHitIndex`) и проверка только соседних.

- **Ожидаемый выигрыш:** дешёвый вариант — **1.5–2×** на `addRoad` (5.4 → 2.7–3.6 мс при 500 рёбрах) почти без риска;
  индекс — **10–20×** (до 0.3–0.6 мс), тогда даже без правки 2 бюджет соблюдается.
- **Риск:** дешёвый — низкий (чистая механика без смены семантики); индекс — высокий: `addRoad` — правило сима
  (влияет на сохранения), нужны побайтово те же причины отказа и разбиения (`sim/roads.test.ts`).

### Правка 4. Один батч оверлея на кадр

Собирать `setData` инструментов в буфер и применять раз за кадр (одна установка `dirty`), не освобождать буферы
источника, если данные того же кадра не изменились (`overlayRaster.ts:127-140`), и не перерисовывать уровни, чей
`levelSquare` не сдвинулся, если изменился только `dirty` от данных (`:155-172`).

- **Ожидаемый выигрыш:** один проход 3×2048² за кадр вместо «грязного» кадра на каждое движение (сейчас события
  схлопываются, но каждая запись освобождает и пересобирает буферы: 3 источника × до 4 слоёв). **Оценка:** GPU-часть
  не измерена; CPU-часть 0.1–0.4 мс/движение снимается полностью.
- **Риск:** низкий/средний — визуально это тот же кадр; нужно проверить порядок слоёв (`overlayStyles.ts:10-32`) и
  что предпросмотр не отстаёт на кадр.

### Правка 5. Дешёвые точечные правки

- `landTool.ts:105`: обернуть `Object.values(buildings).map((b) => b.footprint)` в `makeIdentityCache` по
  `buildings` — 0.003–0.009 мс и аллокации на каждое движение (риск нулевой).
- `roadJunctions.ts:165`: не строить апперон там, где хватает митра ленты — сейчас апперон получает каждый узел со
  сменой типа (`:88`), а это 20 мс из 23.5 на снапшот при 500 рёбрах. **Ожидаемо** 2–5× на этом пути (риск: швы на
  стыках, нужен визуальный контроль).
- `fieldMesh.ts:65`: `edgeDistance` считается на каждую вершину — кэшировать по кольцу или считать расстояние только
  для граничных ячеек (сейчас 11.4 мс на 24-угольное поле).
- `treeScatter.ts:167`: бакеты по bbox лесов на чанк вместо `filter` по всем лесам.
