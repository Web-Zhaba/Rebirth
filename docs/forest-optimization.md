# Оптимизация производительности рендеринга 3D-леса (treeLayer, chunkView, treeScatter)

## 1. Контекст и исходная гипотеза
В первоначальном отчёте архитектурного анализа («重生 Rust FPS提升.docx») покадровый конвейер леса (`chunkView.ts`, `treeLayer.ts`, `treeScatter.ts`) рассматривался как приоритет №1 для переноса на Rust/WASM с ожидаемой трудоёмкостью 2–4 недели.

Перед реализацией WASM-модуля было внедрено микропрофилирование для проверки фактических узких мест CPU:
1. `chunksInView` (поиск видимых чанков, frustum culling).
2. `buildChunks` (генерация, проецирование и подготовка буферов чанков).
3. `thinReach` (бинарный поиск дистанции прореживания).
4. `signature` (строковая сигнатура кадра).
5. `assemble` (копирование в interleaved instance-буферы Three.js).
6. `uniforms` и `host.draw` (Three.js и WebGL).

## 2. Результаты профилирования до оптимизации

### Первоначальный кадр (статичный вид)
* **chunksInView**: 1.05 мс (до 2.2 мс).
* **buildChunks**: спайки до 26.4 мс при выходе за пределы кэша.
* **thinReach / signature / assemble / uniforms / draw**: суммарно < 0.25 мс.

### Стресс-тест в движении над густым биомом (болота / кустарники / тростник)
* **chunksInView**: 2.56 мс (avg), спайки до 9.7 мс.
  * Внутри `chunksInView` совершалось **2042 вызова `centre()` за кадр**, создавая более 6 000 временных массивов координат каждую секунду.
* **source.chunk()**: 2.82 мс на чанк (пики до 5.1 мс).
  * `scatterDetails`: 2.09 мс (74% времени генерации).
  * `scatterTrees`: 0.68 мс.
* **Суммарное время кадра слоя леса**: 4.27 мс (p95 = 9.0 мс, p99 = 10.5 мс).

## 3. Выявленные причины задержек

1. **Избыточные Mercator-проекции и аллокации в `chunkView.ts`:**
   Центр чанка $(cx, cy)$ статичен в системе координат города. Повторный опрос карты высот (`groundAt`), тригонометрический перевод (`toLngLat`) и создание массивов `[mx, my, mz]` 2000 раз в кадре тратили 2.16 мс чистого процессорного времени.
2. **Неэффективный порядок фильтрации в `treeScatter.ts`:**
   Для тростника (`reed`) сетка имеет шаг 2.5 м (до 6400 ячеек на чанк 200×200 м). Для каждой ячейки сначала вызывался тяжёлый тест попадания в полигон (`insideRings`), хотя 85–98% точек в дальнейшем гарантированно отбрасывались по условию малой доли растительности (`h >= share`).
3. **Холостые циклы по всему пространству чанка:**
   Циклы `scatterTrees` и `scatterDetails` сканировали весь чанк $200 \times 200$ м, даже если пересекающий полигон занимал лишь узкую полосу у границы.
4. **Холостые обращения к блокировщику за пределами города:**
   Вызовы `blocker.test` с проверкой хэш-таблицы занятых ячеек производились даже для диких территорий за пределами застройки.

## 4. Применённые оптимизации JavaScript

1. **Мемоизация центров в `treeLayer.ts` / `chunkView.ts`:**
   * Введён хэш-кэш `centreCache: Map<number, [number, number, number]>` с битовым ключом `coordKey(x, y)`.
   * Избавились от аллокаций: метод `centre(x, y, out)` мутирует единый переиспользуемый вектор `tempVec`.
2. **Ранняя отсечка по вероятности (Fast-Path Rejection) в `treeScatter.ts`:**
   * Хэш `h = hash(i, j, s + 2)` проверяется до вычисления координат и до обхода колец полигона: `if (h >= maxShare) continue;`.
3. **Сужение рабочей области генерации по AABB:**
   * Диапазоны циклов $(i, j)$ ограничены пересечением AABB полигонов и границ чанка.
4. **Переиспользуемый типизированный буфер:**
   * Динамический массив `number[]` и вызов `Float32Array.from(out)` заменены на предварительно выделенный `sharedBuffer: Float32Array`.
5. **Отсечка проверки блокировок (`forest.ts`):**
   * Если AABB чанка не пересекает `blocker.box`, вызовы `blocker.test` пропускаются.

## 6. Вывод относительно Rust / WASM
Перенос конвейера леса на Rust **нецелесообразен**:
Текущая нагрузка слоя леса составляет **0.77 мс** на кадр. Накладные расходы на маршалинг данных через границу JS ↔ WASM сопоставимы с этой величиной. Алгоритмическая оптимизация JavaScript полностью устранила узкое место без необходимости усложнять стек проекта.
